# بررسی امنیت، سرعت و تصاویر

این مرحله ساختار و ظاهر سایت را حفظ می‌کند و بر تحویل تصاویر، حجم دادهٔ مرورگر و مرزهای امنیتی پنل متمرکز است. نتیجهٔ آزمون محلی، تضمین امنیت کامل یا سرعت روی هر هاست و اینترنت نیست.

## تصاویر و سرعت

شش عکس موضوعی از فایل‌های PNG اصلی موجود، با ابعاد واقعی بزرگ‌تر و WebP کیفیت ۹۲ بازسازی شدند. عکس ارسالی الهه و ظرافت لوگو حفظ شدند؛ بزرگ‌نمایی مصنوعی یا تغییر چهره انجام نشد. هفت عکس و لوگوی روشن، مجموعاً ۷۸ نسخهٔ واکنش‌گرا دارند. مرورگر AVIF یا WebP متناسب با عرض و تراکم نمایشگر را انتخاب می‌کند؛ نسخهٔ CMS همچنان از بهینه‌ساز Next استفاده می‌کند. راهنمای تولید و نگهداری در [تصاویر](image-optimization.md) است.

در موبایل ۳۹۰ پیکسل با تراکم ۲، حجم عکس هیروی اصلی از ۷۶٬۲۵۲ به ۳۸٬۴۳۲ بایت، هیروی نمونه‌کارها از ۱۸۱٬۴۰۴ به ۸۰٬۹۲۴ و مجله از ۱۹۳٬۷۱۲ به ۸۶٬۲۸۰ بایت رسید. عکس مقاله و جزئیات خدمت نیز از ۹۲٬۰۷۴ به ۶۳٬۸۲۷ بایت رسید. این مقایسه برای همان تصویر قابل مشاهده در هر صفحه است، نه حجم کل صفحه.

| منبع عمومی | قبل، بایت | بعد، بایت |
| --- | ---: | ---: |
| CSS صفحهٔ عمومی | 172584 | 149767 |
| JavaScript مجله | 555614 | 503845 |
| دادهٔ RSC مجله | 98777 | 64937 |
| دادهٔ هشت مقاله در مرز فهرست مرورگر | 42155 | 4719 |

CSS پنل فقط در مسیر مدیریت بارگذاری می‌شود. مقادیر پیش‌فرض تکراری تنظیمات و متن کامل مقاله‌ها از بستهٔ مرورگر فهرست حذف شدند؛ جست‌وجو، فیلتر، مرتب‌سازی و صفحه‌بندی حفظ شده‌اند. پری‌لودر در بازدید اول تب، ۴۲۰ میلی‌ثانیه ورود و ۲۸۰ میلی‌ثانیه خروج دارد و منتظر فونت یا عکس نمی‌ماند. بازدید تکراری و لینک مستقیم به بخش صفحه پیش از نمایش از آن عبور می‌کنند؛ کاهش حرکت، غیرفعال‌بودن ذخیره‌سازی و نبود JavaScript نیز بررسی شده‌اند.

اعداد جدول از Edge و خروجی استاتیک محلی، بدون فشرده‌سازی HTTP و بدون شبیه‌سازی سرعت شبکه یا CPU اندازه‌گیری شده‌اند. این اعداد امتیاز Lighthouse یا Core Web Vitals کاربران واقعی نیستند؛ کیفیت هاست و شبکه باید پس از استقرار اندازه‌گیری شود.

## امنیت

- پردازش scrypt ورود و تغییر رمز به worker pool منتقل شد؛ دو کار هم‌زمان و صف هشت‌تایی دارد. تغییر هم‌زمان یا بازنشانی رمز نمی‌تواند نشست معتبر از رمز قبلی بسازد یا تغییر جدیدتر را بازنویسی کند.
- بدنهٔ درخواست با سقف حجم واقعی جریان و مهلت ۳۰ ثانیه خوانده می‌شود؛ لغو، دریافت ناقص و Content-Length نادرست بررسی شده‌اند.
- فایل آپلودی تنها با امضای ابتدایی پذیرفته نمی‌شود: Sharp آن را کامل باز می‌کند، اطلاعات اضافی و خصوصی را حذف می‌کند و WebP تمیز تحویل می‌دهد. محدودیت حجم، مجموع پیکسل، فریم، هم‌زمانی و زمان تبدیل اعمال می‌شود. رسانه‌های موجود و دیتابیس واقعی تغییر نکردند.
- مسیر دادهٔ متغیر هاست از ردیابی فایل‌های build خارج شد. فایل‌های محیطی، دادهٔ محلی، بکاپ، خروجی بررسی‌ها و Git به‌صراحت از ردیابی بستهٔ سرور مستثنا شدند. بررسی نهایی هر ۱۵ trace سرور، شامل API پنل، هیچ‌یک از این فایل‌ها را نداشت؛ trace خود API از ۱۱۴۴ به ۲۱۳ ورودی رسید. داده و رسانهٔ هاست باید مستقل و روی دیسک دائمی نگهداری شوند.
- بهینه‌ساز تصویر فقط فایل‌های محلی شناخته‌شده و رسانهٔ تأییدشدهٔ CMS را می‌پذیرد؛ SVG و دنبال‌کردن redirect برای آن فعال نیست.
- در اجرای Node، هدرهای جلوگیری از framing، MIME sniffing، محدودسازی قابلیت‌های مرورگر، referrer، COOP و HSTS تولید تنظیم شدند. CSP فعلی، frame/object/base/form target را محدود می‌کند؛ سیاست کامل nonce برای اسکریپت‌ها نیست. مسیر ارسال فرم به FormSubmit حفظ شده است. فایل‌های تصویری دارای هش، کش immutable دارند.

`npm audit` پس از تغییرات هیچ آسیب‌پذیری گزارش‌شده‌ای نشان نداد. Next 16.4.3 و Sharp 0.35.5 با نسخه‌های اصلاح‌شدهٔ [اطلاعیهٔ رسمی امنیتی ۱۴ اکتبر ۲۰۲۶](https://nextjs.org/blog/nextjs-security-update-october-14-2026) تطبیق داده شدند. این بررسی جای به‌روزرسانی و بازبینی دوره‌ای را نمی‌گیرد.

## اعتبارسنجی و حدود تحویل

`npm run check:security` شامل ۳۲ آزمون موفق امنیت و ایمیل است. همهٔ اطلاعات تست ساختگی، دیتابیس موقت مستقل و ایمیل شبیه‌سازی‌شده‌اند؛ رمز، حساب‌ها و دادهٔ واقعی خوانده یا بازنشانی نشدند. خروجی Node و Pages همراه TypeScript ساخته شدند. تصاویر در ۱۰ حالت صفحه/عرض، رفتار پری‌لودر و پنل در هفت حالت و مجله در هفت حالت بررسی شدند. گزارش‌ها و تصاویر محلی در `artifacts/release-audit/` نگهداری می‌شوند.

اجرای پیش‌نمایش موقت Node توسط بررسی خودکار ابزار با پیام `blocked by policy` رد شد؛ دلیل دقیق‌تری ارائه نشد. بنابراین آزمون واقعی پاسخ هدرها از سرور production انجام نشده است؛ تنظیمات هدرها از کد بررسی شدند و API روی دیتابیس مستقل آزموده شد. مرورگر روی خروجی استاتیک انتشار بررسی شد. GitHub Pages هدرهای اختصاصی Next و API پنل را اجرا نمی‌کند؛ فعال‌سازی این بخش‌ها و کنترل HTTPS پس از انتخاب هاست Node لازم است. دامنهٔ نهایی، محتوای واقعی، تأیید دریافت ایمیل و زمان‌بندی بکاپ همچنان به مرحلهٔ استقرار تعلق دارند.
