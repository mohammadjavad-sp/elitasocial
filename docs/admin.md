# پنل مدیریت و دیتابیس

پنل در مسیر `/admin/` روی اجرای Node.js برنامه فعال است. مقاله‌ها، چهار خدمت، نمونه‌کارها، پلن‌ها و تصاویر از همین پنل مدیریت می‌شوند. هر محتوای قابل انتشار وضعیت پیش‌نویس یا منتشرشده دارد. سایت عمومی روی Node فقط موارد منتشرشده را از دیتابیس می‌خواند؛ ذخیرهٔ تغییرات به push یا build دوباره نیاز ندارد.

لوگوی ارسالی برند در پنل و سایت مشترک است. اصلاح املای نام «الیتا سوشیال» روی متن‌های قدیمیِ تنظیمات، محتوای CMS و توضیح تصاویر هنگام خواندن اعمال می‌شود؛ این اصلاح، دیتابیس یا شمارهٔ نسخهٔ محتوا را بازنویسی نمی‌کند و نام‌های سفارشی دیگر را حفظ می‌کند.

دادهٔ اولیه شامل ۸ مقاله، ۴ خدمت، ۸ نمونه‌کار و ۹ پلن است. این اطلاعات فقط یک بار وارد دیتابیس می‌شوند؛ حذف محتوا باعث وارد شدن دوبارهٔ دادهٔ نمایشی نمی‌شود. متن‌های صفحهٔ اصلی، اطلاعات برند، راه‌های ارتباطی و پرسش‌های عمومی از بخش «تنظیمات سایت» مدیریت می‌شوند.

صفحهٔ `/pricing/` و سکشن پلن‌های صفحهٔ اصلی از همان مجموعهٔ «پلن‌ها و قیمت‌ها» استفاده می‌کنند؛ قیمت، امکانات، دوره، وضعیت انتشار و نشان نمایشی را فقط یک بار ویرایش کنید. عنوان، معرفی و یادداشت پایانی پلن‌ها و پرسش‌های عمومی هر دو صفحه نیز از تنظیمات سایت می‌آیند. لینک پلن‌های هر دو صفحه، انتخاب را به فرم مشاورهٔ صفحهٔ اصلی می‌برد.

## تنظیمات سایت

از منوی پنل، «تنظیمات سایت» را باز کنید. تنظیمات در ۹ گروه قرار دارند: برند و ارتباط، ابتدای صفحه، دربارهٔ الیتا، خدمات و همکاری، مزیت‌ها، بخش‌های پایانی، فوتر، پرسش‌های عمومی، و عنوان و توضیح سایت. تصویرهای هیرو و بخش‌های معرفی نیز از رسانه‌ها قابل انتخاب‌اند. عنوان و معرفی پلن‌ها از همین بخش و قیمت و امکانات هر پلن از مجموعهٔ «پلن‌ها و قیمت‌ها» ویرایش می‌شوند.

بین گروه‌ها جابه‌جا شوید و در پایان «ذخیره و اعمال تنظیمات» را بزنید. تغییرات تنها پس از ذخیرهٔ موفق در سایت Node نمایش داده می‌شوند. تعارض ویرایش هم‌زمان، تغییرات داخل فرم را پاک نمی‌کند. پرسش‌های عمومی را می‌توان افزود، مرتب یا حذف کرد؛ فهرست خالی با پرسش‌های اولیه جایگزین نمی‌شود. بخش نظرات مشتریان و تنظیمات آن بنا به تصمیم صاحب سایت حذف شده است.

شمارهٔ تماس و واتساپ، لینک‌های هدر، فوتر، فرم، نمونه‌کار و مزیت‌ها را تغذیه می‌کنند. شمارهٔ نمایشی جداگانه قابل تنظیم است. نام کاربری اینستاگرام و تلگرام را بدون `@` یا به‌صورت لینک کامل معتبر وارد کنید. تغییر عنوان و توضیح سایت، وضعیت `noindex` پیش‌نمایش را عوض نمی‌کند.

تنظیمات در جدول تک‌ردیفی `cms_settings` با شمارهٔ نسخه ذخیره می‌شوند و بکاپ دیتابیس آن‌ها را نیز در بر می‌گیرد. تصویر استفاده‌شده در این تنظیمات از رسانه‌ها قابل حذف نیست مگر ابتدا جایگزین شود. به‌روزرسانی دیتابیس قبلی خودکار است؛ برای ارتقای صریح بدون تغییر حساب‌ها یا بازنشانی محتوای موجود می‌توان `npm run cms:migrate` را اجرا کرد. فیلدهای تازهٔ تنظیمات، مقدار اولیه می‌گیرند و مقدارهای ذخیره‌شده حفظ می‌شوند.

## درخواست‌های مشاوره

فرم صفحهٔ اصلی در اجرای Node، نام، راه ارتباطی، خدمت، توضیح درخواست و پلن انتخابی را در دیتابیس ثبت می‌کند. شمارهٔ فارسی یا عربی پذیرفته و پیش از ذخیره یکسان‌سازی می‌شود. اطلاعات پلن از رکورد منتشرشدهٔ سرور خوانده می‌شود؛ پلن نمایشی، سفارش یا قیمت نهایی ایجاد نمی‌کند. تأیید و کد پیگیری فقط پس از ذخیرهٔ موفق نشان داده می‌شوند. ارسال مجدد همان درخواست در اثر قطع ارتباط، رکورد تکراری نمی‌سازد.

از منوی «درخواست‌های مشاوره» فهرست را باز کنید. جست‌وجو، فیلتر وضعیت و صفحه‌بندی در دسترس‌اند. هر درخواست، کد پیگیری، تاریخ، متن کامل و راه ارتباطی دارد. وضعیت‌های «جدید»، «تماس گرفته شده»، «تکمیل شده» و «بایگانی شده» را می‌توان تغییر داد و یادداشت داخلی افزود. یادداشت فقط برای مدیر نمایش داده می‌شود. حذف دائمی نیاز به تأیید دارد؛ برای نگهداری سابقه، وضعیت بایگانی را انتخاب کنید. در تعارض ویرایش هم‌زمان، تغییرات فرم حفظ می‌شوند.

فهرست، جزئیات، یادداشت‌ها، ویرایش و حذف فقط پس از ورود مدیر و با کنترل‌های نشست و CSRF قابل دسترسی‌اند. ثبت عمومی از همان مبدأ سایت، با محدودیت حجم، اعتبارسنجی سرور، فیلد ضدربات و محدودیت تعداد درخواست انجام می‌شود. کد پیگیری، API عمومی برای مشاهدهٔ اطلاعات فرد ایجاد نمی‌کند. پس از ثبت موفق، مرورگر درخواست را با FormSubmit به ایمیل ارتباطی می‌فرستد. نخستین ارسال، ایمیل فعال‌سازی به مقصد می‌فرستد که مدیر باید تأیید کند. شکست ایمیل به ثبت آسیبی نمی‌زند و پنل مرجع پیگیری است؛ صف ارسال پس‌زمینه یا پیامک وجود ندارد. [راهنمای فعال‌سازی ایمیل](email-delivery.md).

درخواست‌ها در جدول `cms_consultations` داخل همان دیتابیس و بکاپ آن نگهداری می‌شوند. دادهٔ شخصی را در Git یا پوشهٔ عمومی قرار ندهید. روی GitHub Pages ثبت در دیتابیس فعال نیست؛ فرم با سرویس ایمیل ارسال می‌شود و کد پیگیری سایت نمی‌سازد. متن آمادهٔ واتساپ نیز برای ادامهٔ اختیاری گفتگو در دسترس است. تأیید سرویس ایمیل، تضمین رسیدن به Inbox نیست؛ پس از فعال‌سازی مقصد، دریافت واقعی را در Gmail بررسی کنید.

## استفادهٔ محلی

در این workspace دیتابیس و حساب اولیه با `npm run cms:init` ساخته شده‌اند. ایمیل و رمز تصادفی حساب در فایل نادیده‌گرفته‌شدهٔ `.env.local`، با نام‌های `CMS_ADMIN_EMAIL` و `CMS_ADMIN_PASSWORD` هستند. این فایل، دیتابیس و تصاویر بارگذاری‌شده وارد Git نمی‌شوند.

```sh
npm install
npm run dev
```

سپس `http://127.0.0.1:3000/admin/` را باز کنید. پس از اولین ورود، رمز را از بخش «حساب کاربری» تغییر دهید. متغیر رمز اولیه تنها برای ساخت یا بازیابی حساب استفاده می‌شود و تغییر آن به‌تنهایی رمز حساب موجود را عوض نمی‌کند.

برای ساخت حساب روی سیستم یا هاست تازه، مقدارهای زیر را در `.env.local` یا متغیرهای محیطی هاست قرار دهید و سپس `npm run cms:init` را اجرا کنید:

```dotenv
CMS_ADMIN_EMAIL=your-address@example.com
CMS_ADMIN_PASSWORD=a-unique-long-password-with-letters-and-numbers
CMS_ADMIN_NAME=Elita Administrator
```

رمز باید ۱۲ تا ۱۲۸ نویسه و دارای حرف و عدد باشد. `cms:init` حساب موجود را بازنویسی نمی‌کند. اگر بازیابی رمز لازم شد، پس از تنظیم مشخصات جدید، اجرای صریح `npm run cms:init -- --reset-password` رمز همان حساب را عوض و نشست‌های قبلی آن را باطل می‌کند.

## استفاده از پنل

- پیشخوان، تعداد واقعی محتوا و تصاویر را از دیتابیس می‌گیرد.
- در «تنظیمات سایت ← برند و ارتباط»، لینک‌های واتساپ، تلگرام، اینستاگرام، بله، ایتا، روبیکا، ایمیل و شمارهٔ تماس را ویرایش کنید. بله و ایتا نام کاربری یا لینک کامل پروفایل را می‌پذیرند و صفر ابتدای شماره را حفظ می‌کنند. روبیکا اختیاری است؛ تا زمانی که نشانی آن خالی باشد، فقط نشان و عبارت «لینک به‌زودی» نمایش داده می‌شود و قابل کلیک نیست. ایمیل ارتباطی مقصد دکمه‌های ایمیل و پیام‌های فرم است؛ تغییر مقصد به تأیید فعال‌سازی FormSubmit برای ایمیل تازه نیاز دارد. تنظیمات ذخیره‌شدهٔ قبلی، فیلدهای جدید را با مقدار پیش‌فرض دریافت می‌کنند؛ ایمیل پیش‌فرض `elitasociall@gmail.com` است.
- هر مجموعه، جست‌وجو، فیلتر وضعیت، افزودن، ویرایش و حذف دارد. حذف از طریق تأیید جداگانه انجام می‌شود.
- متن مقاله با بخش‌ها، پاراگراف‌ها و فهرست نکته‌ها ویرایش می‌شود. ترتیب بخش‌ها قابل تغییر است؛ ویرایشگر HTML خام ندارد.
- چهار خدمت با شناسه‌های مشخص فعلی مدیریت می‌شوند. برای تغییر اطلاعات یک خدمت، مورد موجود را ویرایش کنید؛ هر شناسه فقط یک بار قابل استفاده است.
- نشان «نمایشی» را پس از جایگزینی مقاله، پروژه یا پلن با اطلاعات تأییدشده بردارید. وضعیت انتشار از این نشان مستقل است.
- تصویر مقاله و خدمت از کتابخانهٔ رسانه انتخاب می‌شود. نمونه‌کار می‌تواند تصویر واقعی داشته باشد یا از قالب تصویری فعلی استفاده کند.
- تصویر PNG، JPG، WebP یا GIF تا ۸ مگابایت با توضیح تصویر پذیرفته می‌شود. فایل تازه کامل رمزگشایی و با کیفیت ۹۰ به WebP تبدیل می‌شود؛ جهت عکس ثابت اصلاح و اطلاعات خصوصی EXIF حذف می‌شوند. انیمیشن تا ۱۰۰ فریم و مجموع ۴۰ مگاپیکسل حفظ می‌شود. پردازش حداکثر ۱۰ ثانیه، دو تبدیل هم‌زمان و خروجی حداکثر ۸ مگابایت دارد. رسانه‌های قبلی بازنویسی نمی‌شوند. تصویر استفاده‌شده در محتوای منتشرشده یا پیش‌نویس، پیش از جایگزین‌شدن قابل حذف نیست.
- ویرایش هم‌زمان با شمارهٔ نسخه بررسی می‌شود. تعارض، خطای ۴۰۹ می‌دهد و متن واردشده در فرم باقی می‌ماند؛ نسخهٔ تازه را بررسی کنید و تغییرات را دوباره اعمال کنید.

نشست مدیر هشت ساعت اعتبار دارد و در کوکی HttpOnly نگهداری می‌شود. درخواست‌های تغییردهنده به نشست معتبر، مبدأ صحیح و توکن CSRF نیاز دارند. رمزها با scrypt و توکن نشست‌ها به‌صورت هش ذخیره می‌شوند؛ ثبت‌نام عمومی وجود ندارد.

پردازش رمز در درخواست‌های HTTP به‌صورت غیرهم‌زمان و با دو کار هم‌زمان و صف محدود انجام می‌شود تا ورود مدیر رندر سایت را متوقف نکند. بدنهٔ درخواست علاوه بر محدودیت حجم، مهلت مطلق ۳۰ ثانیه دارد. آزمون‌های امنیت و ایمیل با `npm run check:security` روی دیتابیس موقت مستقل و ارسال ایمیل شبیه‌سازی‌شده اجرا می‌شوند.

## میزبانی Node

پیش از build نهایی، دامنهٔ عمومی `SITE_URL` و وضعیت `SITE_INDEXING` را مطابق [راهنمای سئو](seo.md) تنظیم کنید. عنوان و توضیح صفحهٔ اصلی از بخش تنظیمات پنل می‌آیند؛ دامنه و اجازهٔ ایندکس، تنظیمات استقرارند. نقشهٔ سایت در اجرای Node ایندکس‌پذیر فقط مقالات و خدمات منتشرشده را می‌خواند و پس از تغییر وضعیت محتوا به build دوباره نیاز ندارد.

برنامه از `node:sqlite` و Node.js نسخهٔ ۲۲٫۱۹ یا جدیدتر استفاده می‌کند. هاست باید یک فرایند دائمی Next.js، دیسک دائمی قابل نوشتن، متغیرهای محیطی و HTTPS داشته باشد. پیشنهاد اولیه برای شروع ۲ گیگ رم است؛ این مقدار برآورد این پروژه است و حداقل رسمی Next.js نیست.

متغیرهای هاست:

```dotenv
CMS_DATA_DIR=/absolute/path/on/persistent-disk/elita-data
CMS_ORIGIN=https://your-domain.example
```

`CMS_ORIGIN` فقط مبدأ HTTPS است و مسیر یا اسلش پایانی ندارد. `DEPLOY_TARGET=github-pages` و `NEXT_PUBLIC_BASE_PATH=/elitasocial` را روی هاست Node تنظیم نکنید. مراحل راه‌اندازی:

```sh
npm ci --include=dev
npm run cms:init
npm run build
npm run start
```

این دستورها راهنمای اجرای هاست هستند؛ build یا آزمون محلی این مرحله اجرا نشده است. متغیر `PORT` پورت برنامه را مشخص می‌کند. در production کوکی ورود Secure است؛ استثنای `CMS_COOKIE_SECURE=false` فقط برای اجرای آزمایشی production روی HTTP محلی در نظر گرفته شده است. اگر پشت reverse proxy قابل اعتماد از محدودسازی بر اساس IP استفاده می‌کنید، `CMS_TRUST_PROXY=true` را تنها وقتی فعال کنید که proxy هدر `X-Forwarded-For` را خودش تنظیم می‌کند.

این نسخه برای یک نمونهٔ برنامه و دیتابیس روی دیسک دائمی همان سرور تنظیم شده است. برای اجرای چند نمونهٔ مستقل روی چند سرور، باید ذخیره‌سازی و دیتابیس اشتراکی مناسب تعریف شود.

## بکاپ و بازیابی

فایل دیتابیس در `CMS_DATA_DIR/elita.sqlite` و تصاویر در `CMS_DATA_DIR/media` هستند. برای بکاپ:

```sh
npm run cms:backup
```

بکاپ در `backups/<timestamp>/` شامل snapshot دیتابیس، تصاویر و manifest ذخیره می‌شود. `CMS_BACKUP_DIR` می‌تواند محل ذخیره را تغییر دهد و باید خارج از `CMS_DATA_DIR` باشد. هنگام بکاپ، بارگذاری یا حذف رسانه را متوقف کنید تا دیتابیس و پوشهٔ تصاویر هماهنگ بمانند. بکاپ حاوی دادهٔ مدیریتی است و باید در فضای خصوصی هاست نگهداری شود.

برای بازیابی، برنامه را متوقف کنید، دیتابیس و پوشهٔ `media` یک بکاپ یکسان را در یک مسیر دادهٔ تازه قرار دهید، `CMS_DATA_DIR` را به همان مسیر بدهید و برنامه را راه‌اندازی کنید. بکاپ‌ها جای دادهٔ فعال بازنویسی نمی‌شوند و فایل‌های موجود به‌صورت خودکار حذف نمی‌شوند.

## GitHub Pages

GitHub Pages همچنان پیش‌نمایش ایستای داده‌های اولیه را منتشر می‌کند و به دیتابیس محلی متصل نیست. صفحهٔ `/admin/` در این نسخه فقط توضیح نیاز به هاست Node را نمایش می‌دهد؛ API مدیریت به خروجی ایستا وارد نمی‌شود. اتصال پنل آنلاین پس از انتخاب هاست و انتقال برنامه انجام می‌شود.

منابع پیاده‌سازی: [استقرار Node.js در Next.js](https://nextjs.org/docs/app/getting-started/deploying)، [میزبانی مستقل Next.js](https://nextjs.org/docs/app/guides/self-hosting)، [SQLite در Node.js 22.19](https://nodejs.org/download/release/v22.19.0/docs/api/sqlite.html)، [ذخیره‌سازی رمز و پارامترهای scrypt در OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
